# Approval Box on peer-channel (c8): target function and data flow

Status: design 0.1, 2026-11-22, Nayuta; step 1 (c8b) built on branch feat/c8b-pc-server (test server only, section 6). Source of truth for the move; [README.md](README.md) keeps describing the running product until each step ships, and is updated in the same diff as the step that changes it.
Inputs: the Owner's rulings of 2026-11-21 (content never stored on the server, only devices decrypt, a decided item goes to the deciding device's history and leaves the server; the server only introduces, content flows AI ↔ device directly; no server-served Web device), peer-channel contract 0.5.1 (kitepon/peer-channel `docs/contract.md`, diagrams `docs/diagrams.md`), login-billing contract 1.20/1.21 (reading 3).

## 1. Who holds what after the move
| Thing | Today | After |
|---|---|---|
| Request body (title, context, options, attachments) | server SQLite `decisions`, attachment files | the AI's local connector outbox (0600 file) until decided; the devices' own history after |
| Answer (option, text, attachments) | server SQLite, then delivered to the connector | device → connector over the peer-channel data channel; the deciding device's history; never the server |
| Decision status (pending, held, answered, cancelled) | server | connector outbox + device history; the server keeps none |
| Account K, passes, contracts | login-billing (library) | unchanged |
| Connections (AI pairings) | server `connections` with token hash | unchanged (id, token hash, label chosen by the person); connector key added through 5.4 admission |
| Device registry | none | server mirror of signed snapshots (public keys only, contract 4.5) |
| Waits, sessions | none | server memory only (contract 6) |
| Push | APNs/FCM with the title | wake only, no content (contract 6.2). iPhone/Mac show the title by decrypting in the Notification Service Extension (peer-channel c6c); Android wakes the app, which dials and then shows the title from what it received |
| Diagnostics | server `diagnostics` (no content) | unchanged |

## 2. Function diagram (target)
| Function | Part | Input → output | Failure |
|---|---|---|---|
| AI asks (MCP `request_decision`, `amend`, `cancel`, `get_decision`, `list_my_decisions`, `resume_decision`) | connector (`approval-box` npm, stdio MCP) + peer-channel connector endpoint | AI → outbox entry → server `wake(K)` → device dials → `request` frame → `ack` | no verified device: the tool answers `no_device` plainly; outbox kept until decided or cancelled |
| Person decides | iPhone/iPad/Mac (Red Shoes), Android/Linux (Indivilia) peer-channel device endpoint | `answer` frame signed by the device key → connector checks (contract 8.3) → `result` to devices | `stale_version` carries `current`; `already_decided` carries the result |
| AI receives the answer | connector daemon | accepted answer → existing delivery to the AI's session (deliveries, channel) | unchanged delivery rules; the body never goes to the server |
| Device history | each device | received requests and results stored on the device (encrypted at rest by the OS store); retention setting stays on the device | another device may miss a decision (accepted by the Owner) |
| Introduce endpoints | server: peer-channel signaling, mirror, TURN credentials, wake | `/pc/v1/*` with `authenticate` = library pass for devices, connection token for connectors; `onPassEnded` wired to the mirror | contract 6 and 14 |
| Admit a device | verified device + new device | contract 5.3 (verify QR / typed code) and 5.2 (with a contract handoff) | `binding_failed` → start again |
| Pair an AI | connector + verified device | product pairing (code, claim) + contract 5.4 `PC1PAIR:` binding | "pairing not finished" with a way to start again |
| BellTeam as a registered client | BellTeam's own connector (owner: Delta) | becomes a peer-channel connector of the person's K through 5.4; the server's scoped client session and the `/v1/decisions` reads go | agreed with Delta before the server routes close |

## 3. Data flow (target)
AI → MCP (stdio) → connector outbox (local, 0600) → `wake(K)` (server → APNs/FCM, no content) → device opens the app or the NSE → signaling `join`/`waits` (server memory) → sealed offer/answer/candidates (server relays sealed bytes) → data channel device ↔ connector (DTLS) → `request` → person decides → `answer` → connector → AI. The server sees: K, connection ids, push tokens, registry public keys, sizes and times (contract 12). It never sees a title, a body, an option, an answer or an attachment.

## 4. What goes from the server (by step, never before the step that replaces it ships)
- `POST /mcp` (remote MCP) and the connector API that carries bodies (`/connector/v1/decisions*`, attachments): a cloud AI without a local connector can no longer reach Approval Box; this follows from the Owner's ruling that content flows AI ↔ device directly.
- `/v1/decisions*`, `/v1/events` with content, attachment routes, push text.
- Tables `decisions`, `decision_events` content, attachment files; purged once, with `secure_delete` and vacuum, and the NAS backup generation replaced (one generation, Owner ruling d04).

6. Production: needs reading 3 in production with `oldHandoff: "off"` (approval-box t30) and Mint's acceptance; the Owner's devices are admitted; then the content routes close and the tables are purged (section 4).

## 7. Step 2: the connector on peer-channel (c8c, test-server line)

Function diagram (connector side; server unchanged except `/pc/v1` of section 6):
| Function | Part | Input → output | Failure / exit |
|---|---|---|---|
| MCP tools | connector/mcp.ts (unchanged tool code) + connector/local-api.ts `LocalApi` | the same `call(method, path, body)` as `Api`, sent over the daemon's local socket | daemon not up: `ensureDaemon`, then retry for 10 s; then `daemon_unreachable` |
| Local decisions | connector/local-box.ts `LocalBox` in the daemon | the `/connector/v1` decision routes (list, create with `check_token` and `duplicate_suspected`, amend, resume, cancel, get, fetched, deliveries, delivery report, setup test start/confirm), ported from server/decisions.ts; store `state/pc/decisions.json` (0600) | same error codes as the server; no server call |
| Transport | connector/pc-daemon.ts: peer-channel `Connector` (`@kitepon/peer-channel/connector` 0.3.0) | create → `request(approval-box/decision@1)`, amend → `amend`, cancel → `cancel`; the device's `approval-box/answer@1` → `LocalBox.answer` → delivery waiting; `onClosed(expired)` → cancelled with reason `expired` | listen gate, backoff and limits of contract 9 |
| Keys | connector/pc-keys.ts | P-256 signing and sealing scalars in `state/pc/keys.json` (0600; contract 3.2 "else a 0600 file"), made once | unreadable file: peer-channel mode off |
| Delivery to the AI | connector/daemon.ts (unchanged loop) | `sync` reads the local deliveries, `deliver` uses channel-delivery.ts, `report` writes the local record, BellTeam wakes read the local status | unchanged |

Data flow: AI → MCP → local socket → LocalBox (title, context, options kept on the PC) → Connector outbox → `wait.open` (server: wait id and alert bit only) → device dials → `request` frame (DTLS) → person answers → `answer` frame → Connector checks (8.3, `validate` with the request's options) → LocalBox answer → `deliveries` → channel → AI. The server sees what section 3 lists; it never receives a title, context, option, answer or delivery text.

Content schemas (the device apps read these; c8d/c8e):
- `approval-box/decision@1`: `{ decision_id, title, context, options: [{ id, label }], recommendation?, urgency: low|normal|high, deadline?, source: { client, session_label, work_label, requester?, requester_bot_id?, connection_label?, test? }, created_at, version }` (`version` is Approval Box's own; the answer refers to peer-channel's `rv`).
- `approval-box/answer@1`: `{ option_id?, text? }`; at least one of `option_id`, `text` or an attachment; `option_id` must be one of that request's options, `text` at most 5000 characters. Answer attachments are the answer frame's blobs (contract 8.2 / 0.5.2: 10 files, 20 MiB each, 50 MiB in total).
- Request images are the request frame's blobs (same limits); `decision@1` itself does not list them.
- A device `hold` (contract 0.5.2 frame `hold { rid, rv, held }`) sets the request aside or back; the connector shows `held`; a later answer still decides.

Mode: the server's `GET /v1/auth/config` says `peer_channel: true` when `/pc/v1` is mounted. The daemon alone decides the connector's path at start (`startDaemonPeerChannel`): peer-channel only when the profile holds `state/pc/keys.json` and an admission (`state/pc/admission.json` from setup, or the outbox state it became) AND the flag is true; it writes `state/pc/mode.json` (`pc` or `server`, with the reason) and one named log line, and MCP follows that file for the running daemon, so MCP and daemon never take different paths. A flag that cannot be read, or an endpoint that cannot start, is retried with a named line (MCP then fails as `daemon_unreachable`), never a silent switch to today's path. Without keys or admission everything is today's path.

Pairing (contract 5.4, c8c part 2): when the server offers peer_channel, `npx approval-box setup` makes the keys before the product pairing and shows the QR as `PC1PAIR:<pairing code>:<fp>:<secret>` (for the app's own reader only; no URL line) and, beside the pairing code, the 16-character typed secret. After the product claim, the connector runs the binding as the starter (`@kitepon/peer-channel/pairing`): one verify id per secret (derived from the secret), pc1-join with `connection_id`, the approver's pc1-admit tagged over join and admit; the admitted snapshot goes to `state/pc/admission.json`. A failed or expired binding is reported by name and the connection keeps working on today's path. App side (c8d Red Shoes, c8e Indivilia): the reader takes the pairing code from `PC1PAIR` for the product's lookup and claim, then joins the verify id derived from the secret; the connector opens its verify ids only after the claim (it has no token before), so the app retries `verify.join` on `unknown_verify` until joined (5 minutes).

Known requirement: peer-channel mode needs Node ≥ 24 on the PC (peer-channel's engines) and node-datachannel's native module beside the connector's runtime; today's path keeps the connector's Node ≥ 20.

Built in c8c part 1: LocalBox, LocalApi and the socket, the daemon running the Connector, the keys file, and an end-to-end test. Part 2: the server flag, the daemon's mode decision with `mode.json`, setup's `PC1PAIR` binding; the end-to-end test now pairs through the binding (the phone approves the connector's `PC1PAIR` text), lets the daemon decide the mode, and runs request → device answer → the AI's channel with the server database holding no title, context or answer; a second case checks that a server without `/pc/v1` gives today's path with the named line. Part 3: request images (`image_paths` are staged by the MCP process as 0600 files in `state/pc/uploads/`, taken by LocalBox, kept in `state/pc/files/<decision>/`, and sent as blobs after the request frame), answer attachments (blobs checked by peer-channel, kept in `state/pc/files/<decision>/`, listed in the delivery text, saved for the AI by the unchanged `saveAll` through the local `download`, and returned by `get_attachment`), and the device `hold` (status `held`, back to `pending`; list and get show it). The end-to-end test sends an image to the phone, gets a hold and an answer with a photo back, and checks both files byte for byte on the PC and absent from the server's files. After part 3:
- Re-binding (contract 0.5.3): `npx approval-box setup --rebind` binds a new key set to the already-paired connection without a new product pairing (connector/pc-rebind.ts). The keys are made in memory and saved only after the binding succeeds; the QR is `PC1PAIR::<fp>:<secret>` (empty pairing code) with the typed secret; the approver skips the product claim and tombstones the connection's other connector keys in the snapshot that adds the new one; the connector writes the new admission, drops only the registry part of its outbox state (the waiting requests and tombstones stay) and restarts the daemon. A failed binding keeps the previous keys and is reported by name.
- Setup check (contract Q8): a test answer is checked on the PC; after `confirm_setup_test` passes, the daemon tells the server only `POST /connector/v1/setup-test/verified { client, os }`, which marks that client's setup check passed for the connection and sets `users.setup_verified_at` (no decision, no answer, no code; the bit is the connector's own statement under its connection token). Sent again up to 5 times when the server cannot be reached.

## 8. Local dev server (for the app builders, never deployed)

`npm run dev:server` (packages/server/src/dev.ts) runs the whole Approval Box server on the builder's own machine: the real `createApp`, the library (login-billing 0.13.0) and `/pc/v1`, with login-billing's TestKit (`@kitepon/login-billing/testing`) as the library's `fetch`, its fake stores and fake web clients. It listens only on 127.0.0.1 (`PORT`, default 8788) and refuses to start when `PUBLIC_URL` is not a loopback http URL, so it cannot be deployed by mistake. Data goes to `DEV_DATA` (default `./.dev-data`, git-ignored; never `APPROVAL_BOX_DATA`). The fake person is `DEV_SUBJECT` (default `dev-person`); its K (Apple and Google) is exempt, so paid routes and `join` pass without a store.
- Sign in from a device or a script: `POST /auth/v1/signin/nonce` → `POST /dev/id-token { provider: "apple" | "google", nonce, sub? }` (answers `{ id_token, aud }`; Apple aud `dev.kitepon.approvalbox`, Google aud `dev-google-client.apps.local`) → `POST /auth/v1/signin { provider, idToken, nonce }` gives a real pass from this server. Web sign-in: take `providerUrl` from `websignin/start`, `POST /dev/websignin { providerUrl, sub? }` answers the callback `location` the browser would follow.
- Then everything else is the real server: `/v1`, `/connector/v1`, pairing, `/pc/v1` (signaling, mirror, TURN with an empty list). A wake is one local log line (`wake alert=1|0`), nothing is sent.
- Not covered: real Apple/Google sign-in and stores, real APNs/FCM pushes, TURN, and anything a public URL needs (verified app links, the web sign-in return through `https://<origin>/app/websignin`).
- Test: packages/server/test/dev.test.ts (a non-loopback `PUBLIC_URL` is refused; a fake sign-in gets a pass that passes a paid route).

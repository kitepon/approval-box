## 3. Data flow (target)
AI → MCP (stdio) → connector outbox (local, 0600) → `wake(K)` (server → APNs/FCM, no content) → device opens the app or the NSE → signaling `join`/`waits` (server memory) → sealed offer/answer/candidates (server relays sealed bytes) → data channel device ↔ connector (DTLS) → `request` → person decides → `answer` → connector → AI. The server sees: K, connection ids, push tokens, registry public keys, sizes and times (contract 12). It never sees a title, a body, an option, an answer or an attachment.

## 4. What goes from the server (by step, never before the step that replaces it ships)
- `POST /mcp` (remote MCP) and the connector API that carries bodies (`/connector/v1/decisions*`, attachments): a cloud AI without a local connector can no longer reach Approval Box; this follows from the Owner's ruling that content flows AI ↔ device directly.
- `/v1/decisions*`, `/v1/events` with content, attachment routes, push text.
- What stays after the close (no content): sign-in and passes (`/auth/v1`), `/v1/me` (account and `plan`, the entitlement source for every client including BellTeam's session), the product pairing and connection routes (`POST /connector/v1/pairing` with `client: "bellteam"`, its claim and the session it yields, `/connector/v1/connection`, connection removal), `/pc/v1`, billing, diagnostics. A BellTeam session keeps only `GET /me` from its allowed list; its decision, answer, hold, attachment and SSE rows go with the content routes.
- Tables `decisions`, `decision_events` content, attachment files; purged once, with `secure_delete` and vacuum, and the NAS backup generation replaced (one generation, Owner ruling d04).

Data flow: AI → MCP → local socket → LocalBox (title, context, options kept on the PC) → Connector outbox → `wait.open` (server: wait id and alert bit only) → device dials → `request` frame (DTLS) → person answers → `answer` frame → Connector checks (8.3, `validate` with the request's options) → LocalBox answer → `deliveries` → channel → AI. The server sees what section 3 lists; it never receives a title, context, option, answer or delivery text.

Content schemas (the device apps read these; c8d/c8e):
- `approval-box/decision@1`: `{ decision_id, title, context, options: [{ id, label }], recommendation?, urgency: low|normal|high, deadline?, source: { client, session_label, work_label, requester?, requester_bot_id?, connection_label?, test? }, created_at, version }` (`version` is Approval Box's own; the answer refers to peer-channel's `rv`).
- `approval-box/answer@1`: `{ option_id?, text? }`; at least one of `option_id`, `text` or an attachment; `option_id` must be one of that request's options, `text` at most 5000 characters. Answer attachments are the answer frame's blobs (contract 8.2 / 0.5.2: 10 files, 20 MiB each, 50 MiB in total).
- Request images are the request frame's blobs (same limits); `decision@1` itself does not list them.
- A device `hold` (contract 0.5.2 frame `hold { rid, rv, held }`) sets the request aside or back; the connector shows `held`; a later answer still decides.

Mode: the server's `GET /v1/auth/config` says `peer_channel: true` when `/pc/v1` is mounted. The daemon alone decides the connector's path at start (`startDaemonPeerChannel`): peer-channel only when the profile holds `state/pc/keys.json` and an admission (`state/pc/admission.json` from setup, or the outbox state it became) AND the flag is true; it writes `state/pc/mode.json` (`pc` or `server`, with the reason) and one named log line, and MCP follows that file for the running daemon, so MCP and daemon never take different paths. A flag that cannot be read, or an endpoint that cannot start, is retried with a named line (MCP then fails as `daemon_unreachable`), never a silent switch to today's path. Without keys or admission everything is today's path.

Pairing (contract 5.4, c8c part 2): when the server offers peer_channel, `npx approval-box setup` makes the keys before the product pairing and shows the QR as `PC1PAIR:<pairing code>:<fp>:<secret>` (for the app's own reader only; no URL line) and, beside the pairing code, the 16-character typed secret. After the product claim, the connector runs the binding as the starter (`@kitepon/peer-channel/pairing`): one verify id per secret (derived from the secret), pc1-join with `connection_id`, the approver's pc1-admit tagged over join and admit; the admitted snapshot goes to `state/pc/admission.json`. A failed or expired binding is reported by name and the connection keeps working on today's path. App side (c8d Red Shoes, c8e Indivilia): the reader takes the pairing code from `PC1PAIR` for the product's lookup and claim, then joins the verify id derived from the secret; the connector opens its verify ids only after the claim (it has no token before), so the app retries `verify.join` on `unknown_verify` until joined (5 minutes).

  | MCP tools (relay) | connector/mcp.ts with `hostedSocket()` | every tool call → `LocalApi(<socket>)`; no `config.json` token is needed; the seat daemon is still started for delivery | hosted daemon not paired: `503 not_paired` / `starting` by name; socket down: `daemon_unreachable`; never today's `/mcp` |
  | Delivery (relay) | connector/daemon.ts runDaemon in the seat's home | `api` = the hosted socket; polls `GET /deliveries` every 2 s, delivers to the seat's channels, reports with `POST /deliveries/:id`, BellTeam wakes as before; no keys, no endpoint of its own | socket errors are logged and retried (the same loop as today) |
  | Hosted daemon | connector/daemon.ts `--hosted` | the decision store and the peer-channel endpoint only; it runs no delivery loop (the seats' daemon does) | unchanged |
  | Blobs on the socket (every mode) | connector/local-api.ts `serveLocal` / `LocalApi` | `POST /uploads { name, content_type, data (base64) }` → `{ id }` staged in `state/pc/uploads/`; `GET /decisions/:id/attachments/:aid` → `{ data (base64) }`; requests up to 32 MiB per line | the same `validation_failed` / `not_found` as the files |

  Data flow: AI → MCP (seat) → hosted socket → LocalBox (hosted) → Connector → device → answer → `deliveries` (hosted) → seat daemon polls → seat channel → AI. The socket has no caller identity: whoever can open it reads the account's decisions, the same trust as one shared `~/.approval-box` for all seats today; the supervisor (BellTeam) decides who can open it. The switch is made only after the hosted daemon is paired (before that every request tool answers `not_paired`).

## 8. Local dev server (for the app builders, never deployed)

`npm run dev:server` (packages/server/src/dev.ts) runs the whole Approval Box server on the builder's own machine: the real `createApp`, the library (login-billing 0.13.0) and `/pc/v1`, with login-billing's TestKit (`@kitepon/login-billing/testing`) as the library's `fetch`, its fake stores and fake web clients. It listens only on 127.0.0.1 (`PORT`, default 8788) and refuses to start when `PUBLIC_URL` is not a loopback http URL, so it cannot be deployed by mistake. Data goes to `DEV_DATA` (default `./.dev-data`, git-ignored; never `APPROVAL_BOX_DATA`). The fake person is `DEV_SUBJECT` (default `dev-person`); its K (Apple and Google) is exempt, so paid routes and `join` pass without a store.
- Sign in from a device or a script: `POST /auth/v1/signin/nonce` → `POST /dev/id-token { provider: "apple" | "google", nonce, sub? }` (answers `{ id_token, aud }`; Apple aud `dev.kitepon.approvalbox`, Google aud `dev-google-client.apps.local`) → `POST /auth/v1/signin { provider, idToken, nonce }` gives a real pass from this server. Web sign-in: take `providerUrl` from `websignin/start`, `POST /dev/websignin { providerUrl, sub? }` answers the callback `location` the browser would follow.
- A store pass for a non-exempt person (so the library's QR handoff can run: approver has a store pass, starter is a signed device of the same account): sign in with any `sub` other than `DEV_SUBJECT`, then `POST /dev/store-purchase { provider: "apple" | "google", k }` (`k` = the `k` from `/auth/v1/signin`, optional; it binds the purchase to that account as the stores' account mark). It puts an active 30-day subscription for `dev.kitepon.approvalbox.monthly` into the fake store and answers `{ route: "/auth/v1/receipt", receipts: [...] }`; the app posts `{ receipts }` to that route with its pass (`Authorization: Bearer <pass>`) and gets the store entitlement. Google receipt: `{ store: "google", productId, purchaseToken }`; Apple receipt: `{ store: "apple", transactionId }`.
  ```
  curl -s :8788/dev/id-token -d '{"provider":"google","sub":"dev-buyer","nonce":"<n>"}'   # then /auth/v1/signin -> pass, k
  curl -s :8788/dev/store-purchase -d '{"provider":"google","k":"<k>"}'                    # -> { route, receipts }
  curl -s :8788/auth/v1/receipt -H "authorization: Bearer <pass>" -d '{"receipts":[...]}'  # -> entitlements
  ```
- Then everything else is the real server: `/v1`, `/connector/v1`, pairing, `/pc/v1` (signaling, mirror, TURN with an empty list). A wake is one local log line (`wake alert=1|0`), nothing is sent.
- Lab pairing (c8h, for a hosted connector without a phone): `packages/server/src/dev-approve.ts` is a fake approver device, so the connector's pairing (contract 5.4) can run once with no phone and no Owner. Never on the test or production server: it takes only a loopback `DEV_URL` (default `http://127.0.0.1:8788`, checked with `assertLoopback`) and needs the dev server's `/dev/id-token`.
  1. Start the dev server: `cd packages/server && npm run dev:server` (data in `DEV_DATA`).
  2. On the connector side: `APPROVAL_BOX_SERVER=http://127.0.0.1:8788 approval-box pair --json` (or `--server URL`); take `qr_text` (`PC1PAIR:<code>:<fp>:<secret>`) from its `waiting` line.
  3. Within the 5 minutes of the claim: `cd packages/server && npm run dev:approve -- '<PC1PAIR text>'`. It signs in as `DEV_SUBJECT` through the fake sign-in above, reads the code in the text and claims the pairing as that account (looked up at `GET /v1/pairing/lookup`, claimed at `POST /v1/pairing/{id}/claim`; an empty code, i.e. `pair --json --rebind`, skips the claim), then approves the connector's keys with `TestDevice.approveConnector`. It prints one JSON line, `{approved:true, connection_id, k}` or `{approved:false, error}` (exit 1); no key and no pass is printed.
  4. `DEV_DATA/lab-approver.json` (0600) keeps the approver's own device keys (signing and seal private scalars) and the latest registry snapshot it signed, so a second pairing or a `--rebind` builds on the same registry. Delete it together with the dev database, never alone.
- Not covered: real Apple/Google sign-in and stores, real APNs/FCM pushes, TURN, and anything a public URL needs (verified app links, the web sign-in return through `https://<origin>/app/websignin`).
- Test: packages/server/test/dev.test.ts (a non-loopback `PUBLIC_URL` is refused; a fake sign-in gets a pass that passes a paid route).

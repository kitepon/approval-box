## 90066748から501c880への対応

差分の機能変更は8895ff8（schema9→10、Bridge session/seq/終端/closed journalと同通話追跡）。fbf78a5はshutdown試験でtimeout時のreader取消を行う試験変更。全体の他責務/公開窓口は同じで、PR15の構造整理は含まない。容量是正は常駐ログwriter、harnessの再生成できる登録設定の失敗temp回収、対応試験・版metadataを変更する。資格・結果不明の状態は共通writerの既定でtempを保全する。詳細は[保存図](storage-lifecycle.md)を参照する。

## データフローと状態の所有

Web/native→署名つきの要求（Web・新しい形のアプリ。Webは子の端末としてスマホに入れてもらう）またはsession認証HTTP→Accounts/Decisions/Attachments→SQLiteと添付→commit後EventHub→SSE/APNs/FCM→再GET（APNs・App Store照会・Google Play/FCMのJWTの署名は、サーバー→unix ソケット→認証モジュール→署名で、鍵はサーバーに入らない。モジュールが無ければ環境の鍵）。AI→stdio MCP/remote MCP→connection認証→Decisions→answer waiting。PC配送はdaemon journal→外部親channel→state照合→報告後回収。受け口が無く諦めた配送は、控えたBellTeam申請元へ起こし知らせ（wake journal→BellTeam MCP sendmessage一度→席の再開→AIのresume_decisionで保存済みの答えを取得）。Bridge配送はSQLite journal→call_send一度（HTTPはサーバー→unix ソケット→認証モジュール→call.kitepon.dev で、bearer はモジュールが付ける。モジュールが無ければヘッダーのファイル）→Bridge受付を確定（宛先の起床と復旧はBridge）。診断logはこれらの業務状態から独立し、失敗しても配送結果を書き換えない。

機能表から実ファイル・関数・保存/readerを辿る。native/Steer/Aiterm/Bridge/BellTeam本体/ホストの内部とThroughlineは担当外（BellTeamは公開MCPの `sendmessage` だけを使い、席を起こす処理はBellTeam所有）。図の正本はこの入口とリンク先であり、人間向けの画像生成物は必須にしない。
